# Прокси через собственный домен (Алматы): отчёт и план изменений

Только исследование. Код, production, публикация и деплой не затрагиваются.

## 1. Где сейчас происходят обращения к бэкенду

| Тип запроса | Текущий путь | Через клиентский failover |
|---|---|---|
| Данные статей, `disease_articles`, `image_annotations` (PostgREST) | Supabase client → активный маршрут (`api2` для production, `api3` для `.lovable.app`) | да |
| Авторизация (`/auth/v1/*`, refresh) | тот же маршрут, сессия в `localStorage` | да (плюс `runAuthRace`) |
| Edge Functions | частично `supabase.functions.invoke`, частично прямые URL `/functions/v1/...` | частично |
| Публичные изображения и видео (Storage) | прямые URL в `<img>`/`<video>` | нет |
| Подписанные файлы (signed URL, 1 час) | прямые URL Storage | нет |
| Realtime / WebSocket (`BatchAnalysisDialog`, `ArticleMarkdownEditor`) | WSS напрямую | нет |

Вывод: именно то, что не проходит через fetch-failover (картинки, signed URL, WebSocket), и даёт у пользователей из РФ таймауты; 403 приходят из PostgREST/Storage при отсутствующем или устаревшем токене после провала маршрута.

## 2. Реализуемость

**Реализуемо**
- Same-origin reverse proxy на nginx в backend-приложении Timeweb: `/api/`, `/auth/`, `/media/`, `/fn/`, `/rt/` (с `Upgrade` для WebSocket).
- Первым переводом — только публичные изображения (`/media/`): без токенов, без cookies, кэшируется, откат мгновенный.
- Кэширование Storage на nginx (`proxy_cache`, ключ по пути + query).

**Требует проверки**
- Signed URL: подпись привязана к хосту Storage, требуется точное сохранение query-параметров.
- Стриминг Edge Functions (SSE/чанки): нужен `proxy_buffering off`.
- Realtime через прокси: WSS Upgrade, таймауты, keepalive.
- Cookies/refresh: сейчас сессия в `localStorage`; перевод на httpOnly cookies — отдельная задача, не в первом шаге.

**Не рекомендуется**
- Удалять существующий failover и маршруты `api2`/`api3`.
- Включать прямой Supabase (`VITE_ALLOW_DIRECT_SUPABASE`) как единственный путь: проверки из дата-центров не отражают домашние и мобильные сети РФ.
- Править общий `nginx.conf` в текущем репозитории до изоляции: авто-деплой доставит его в production.

## 3. Ограничения инфраструктуры (по факту проверки Timeweb API)

- Production app `225711` — тип backend/Docker, Амстердам, IP `147.45.173.6`, домены `tarusin.pro` и служебный `...-d7ac.twc1.net`, авто-деплой включён.
- KZ app `245983` — тип frontend/static, Алматы, IP `188.225.31.33`, домен `...-7851.twc1.net`. `Dockerfile` и `nginx.conf` игнорируются, env пустые — как песочница для прокси не годится.
- Оба приложения тянут один и тот же репозиторий и коммит, поэтому любое изменение конфигурации nginx попадёт и в production.
- Разница в пререндере (SSG на `tarusin.pro`, SPA-fallback на служебном домене) объясняется типом приложения, а не разными коммитами.

Следствие: нужно отдельное **backend**-приложение в Алматы, иначе шаг с прокси невозможно провести изолированно.

## 4. План изменений (по шагам, каждый — с отдельным подтверждением)

1. **Изоляция.** Создать в Timeweb Алматы новое приложение типа backend (Docker) на отдельной ветке репозитория. Клиент не меняется.
2. **Прокси без клиента.** В этой ветке добавить `nginx.conf` с `location /media/` на Storage. Проверка только `curl`: код 200, Content-Type, кэш-заголовки, время ответа.
3. **Изображения.** Ввести хелпер построения URL картинок с переключателем через env; включить прокси-хост только в preview. Проверить статьи и галереи.
4. **Данные.** Добавить `/api/` и перевести PostgREST-маршрут как ещё один кандидат failover — без удаления `api2`/`api3`.
5. **Функции.** Добавить `/fn/` с отключённой буферизацией, проверить стриминг AI и парсеры.
6. **Авторизация.** Добавить `/auth/`, оставив `localStorage`. Cookies/refresh — отдельной задачей позже.
7. **Realtime.** Добавить `/rt/` с WebSocket Upgrade, проверить батч-анализ и совместное редактирование.
8. **Production.** Переносить в `main` только после успешных тестов из домашних и мобильных сетей РФ, по одному типу запросов.

## 5. Что будет затронуто (когда дойдёт до реализации)

Файлы: `nginx.conf` (в изолированной ветке), `src/lib/backendEndpoints.ts`, `src/lib/backendRouteManager.ts`, `src/lib/backendFailover.ts`, хелпер URL изображений (`src/lib/storageImage.ts`). Защищённые контракты маршрутов статей, `diseaseLoader`, редактора и галерей не трогаются.

Переменные окружения: адрес прокси-хоста и флаг его включения (по одному на тип запроса), существующий `VITE_ALLOW_DIRECT_SUPABASE` сохраняется.

Supabase: изменений схемы не требуется; при переходе на cookies потребуется проверка настроек redirect URL.

Timeweb: новое backend-приложение в Алматы, домен для прокси, сертификат, отдельная ветка деплоя.

## 6. Тесты из сетей РФ (домашняя и мобильная)

Загрузка статей и картинок галерей; вход и обновление сессии; воспроизведение видео; открытие signed-документов; стриминг AI; `image_annotations`; отсутствие прямых обращений к `*.supabase.co` в Network; отсутствие 403 и таймаутов.

## Рекомендация

Начинать можно, но только в новом backend-приложении Timeweb в Алматы на отдельной ветке, шагами 1–2, без изменений клиента и production.
